# macOS v0.1 release qualification

This document is the release-engineering gate for the first public Cheat Dock macOS release. It does **not** authorize a tag or GitHub Release by itself.

## Current v0.1 distribution decision

Cheat Dock v0.1 will be distributed directly from the official `ririri-rgb/cheat-dock` GitHub Releases page as a universal macOS DMG.

The current v0.1 distribution model is:

- universal `arm64 + x86_64` app and DMG;
- **ad-hoc signed** with `APPLE_SIGNING_IDENTITY=-`;
- **not Developer ID signed**;
- **not Apple-notarized**;
- no stapled Apple notarization ticket;
- no Apple Developer Program requirement for v0.1;
- first-launch Gatekeeper friction is expected on a browser-downloaded/quarantined copy;
- users who choose to proceed must use macOS's official per-app Privacy & Security approval flow, not disable system security globally.

Do not describe this build as Apple signed, a verified developer build, notarized, trusted by Gatekeeper, or malware-checked by Apple. Also do not call the current app simply “unsigned”: the production candidate has an ad-hoc code signature, and qualification verifies that exact state.

Developer ID signing and notarization remain available as a **future optional verified-distribution lane** if the project later joins the Apple Developer Program. The existing protected workflow is intentionally retained for that future use.

## Release boundary

The candidate version is `0.1.0`, but this qualification phase must not create:

- a `v0.1.0` tag;
- a GitHub Release;
- permanent/public release assets;
- Apple Developer certificates or API keys;
- notarization submissions;
- Mac App Store records or submissions.

GitHub Actions artifacts generated by the qualification workflow are temporary test artifacts only.

`package.json`, the root `package-lock.json` package, and `src-tauri/Cargo.toml` mirror the authoritative Tauri version. `npm run release:identity` fails if they drift or if the frozen product/bundle identity changes unexpectedly.

### Bundle identifier is a hard data-identity gate

The identifier remains `dev.cheatdock.app`. Tauri resolves `app_data_dir` from the bundle identifier, and PR #6 has already placed qualified user Markdown under that identity. Changing it without a separately qualified migration could strand existing user data.

For macOS, user data remains conceptually under:

```text
~/Library/Application Support/dev.cheatdock.app/user-data/
```

Treat a candidate whose actual signed app bundle identifier differs from `dev.cheatdock.app` as a release blocker and stop upgrade qualification.

## GitHub repository protection

Before public distribution, `main` must be protected against accidental source replacement. The current repository policy uses the active `Protect main` ruleset with:

- changes through pull requests;
- zero required human approvals, appropriate for the current solo-maintainer setup;
- required normal CI checks `frontend` and `macos-rust`;
- force pushes blocked;
- branch deletion blocked.

Release-only jobs are deliberately not required status checks because they do not run on every pull request.

## Production candidate workflow

The v0.1 GitHub-distribution path uses the existing `production-universal` job in `.github/workflows/macos-release-qualification.yml`.

The release-shaped build is:

```sh
npm ci
npm run release:check
rustup target add aarch64-apple-darwin x86_64-apple-darwin
APPLE_SIGNING_IDENTITY=- npm run tauri build -- --target universal-apple-darwin --bundles app,dmg
```

`APPLE_SIGNING_IDENTITY=-` is an **ad-hoc signature**, not Developer ID signing.

The production verifier must confirm:

- generated `.app` exists;
- generated DMG exists and mounts;
- DMG contains Cheat Dock and an Applications destination;
- `CFBundleIdentifier` is `dev.cheatdock.app`;
- `CFBundleName` is `Cheat Dock`;
- `CFBundleExecutable` is `cheat-dock`;
- `CFBundleShortVersionString` and `CFBundleVersion` match `0.1.0`;
- `LSMinimumSystemVersion` matches the configured minimum;
- executable contains both `arm64` and `x86_64` slices;
- `codesign --verify` succeeds;
- signature is specifically ad-hoc and not `Developer ID Application`;
- no release app enables `com.apple.security.get-task-allow`;
- no unexpected custom entitlement is introduced;
- candidate checksums are recorded.

The workflow uploads a short-lived Actions artifact named `cheat-dock-v0.1-candidate-universal-adhoc`. It is a qualification artifact, not a public end-user release asset.

## Candidate immutability

The policy/docs PR itself must not become the physical release artifact. After this PR is merged, manually dispatch the release-qualification workflow from the exact intended `main` commit.

Freeze the resulting candidate as one tuple:

```text
release_candidate_sha
workflow run ID
Actions artifact ID
Actions artifact digest
exact DMG filename
exact DMG SHA-256
app ZIP SHA-256
```

Physical qualification must use the same run and same artifact. Do not rebuild or silently switch to a newer artifact after testing begins.

If release-relevant source changes are merged after candidate freeze, start over with a new SHA, new workflow run, new checksums, and new physical qualification.

## Checksums and trust model

The v0.1 public distribution model does not have Apple developer-identity verification. Therefore release consumers must be able to confirm what they downloaded from the official repository.

The future public Release should contain only the minimum necessary assets:

```text
Cheat-Dock_0.1.0_universal.dmg
SHA256SUMS.txt
```

The actual Tauri-generated DMG filename may differ during qualification; record that exact name before any later release-asset naming decision.

`SHA256SUMS.txt` must contain the exact DMG SHA-256. The workflow may also checksum the retained app ZIP used for qualification.

Do not confuse:

- **Actions artifact digest** — digest of GitHub's Actions artifact container; and
- **DMG SHA-256** — digest of the actual DMG that an end user would download.

The public integrity value that matters most is the exact DMG SHA-256. SHA-256 helps detect artifact mismatch or tampering relative to the published value, but it is not a substitute for Apple Developer ID identity verification or Apple notarization.

## Real Gatekeeper qualification

Local build launch alone is insufficient. Physical qualification must obtain the exact candidate through a normal browser download path from the GitHub Actions UI so macOS can apply normal quarantine metadata, approximating the eventual GitHub Release path.

Before first launch, read-only inspection may verify the presence of quarantine metadata. Do not remove, rewrite, or bypass quarantine as part of the test.

A candidate that lacks quarantine must not receive a physical Gatekeeper PASS merely because no warning appeared. Re-download it normally through a browser and repeat the check.

### Expected first-launch behavior

Because v0.1 is not Developer ID signed or notarized, macOS may initially block launch. That initial block is an **expected limitation**, not by itself a product failure.

The essential qualification is:

- DMG mounts and app bundle is intact;
- initial macOS security decision is observed on a quarantined browser download;
- the app is not genuinely corrupt/damaged;
- the user can choose the official per-app approval path;
- after explicit approval, the app launches and remains usable.

Treat these as failures:

- DMG cannot mount;
- app bundle is structurally corrupt;
- `codesign --verify` fails;
- required architecture is missing;
- candidate is actually damaged/corrupt;
- app still cannot launch after the official per-app approval;
- app crashes or fails its smoke tests.

Do not hard-code qualification to one exact Gatekeeper dialog sentence because wording varies by macOS release.

## Official per-app approval path

Apple's current support documentation says that after first attempting to open an app that is not notarized or is from an unidentified developer, a user who is certain of the source can go to **System Settings → Privacy & Security**, use **Open Anyway / このまま開く**, and confirm the app. Wording may differ by macOS version.

References:

- https://support.apple.com/102445
- https://support.apple.com/guide/mac-help/mh40616/mac

The installation documentation must never instruct users to disable Gatekeeper globally, disable SIP, or remove quarantine attributes as the normal installation method.

Before a user chooses Open Anyway, README guidance must tell them to verify:

- repository owner: `ririri-rgb/cheat-dock`;
- the intended GitHub Release;
- exact filename;
- published SHA-256.

## Fresh-install physical qualification

Use the exact frozen ad-hoc candidate, downloaded through a normal browser path.

Record macOS version, machine architecture, workflow run ID, artifact ID/name, DMG filename, DMG SHA-256, app version, and result.

Fresh-install gate:

- [ ] Candidate source SHA and workflow run are the frozen tuple.
- [ ] Downloaded DMG SHA-256 matches `SHA256SUMS.txt`.
- [ ] Download path preserved normal macOS quarantine behavior.
- [ ] DMG opens normally.
- [ ] Applications destination is present and usable.
- [ ] Cheat Dock copies to Applications.
- [ ] First normal launch records the actual Gatekeeper outcome.
- [ ] If blocked, the official per-app Privacy & Security approval succeeds.
- [ ] Cheat Dock launches after approval.
- [ ] Menu-bar icon and popup work.
- [ ] Foreground app detection works without Accessibility permission.
- [ ] Search and Japanese IME work.
- [ ] Shortcut display/Record works.
- [ ] Command values remain literal.
- [ ] A personal item can be created.
- [ ] Restart preserves the personal item.
- [ ] Open Data Folder points to the expected identifier-scoped Application Support location.
- [ ] No unexpected Accessibility, Full Disk Access, Screen Recording, Automation, microphone, camera, account, cloud, telemetry, or other new permission/connection is requested.

## Upgrade and user-data retention qualification

Upgrade qualification is a v0.1 release gate because Cheat Dock already has PR #6 file-backed user data.

Before upgrade:

1. back up `~/Library/Application Support/dev.cheatdock.app/` locally;
2. record filenames, stable IDs, file count, and optionally local SHA-256 values;
3. do not upload personal Markdown contents to GitHub or workflow artifacts.

Install the exact frozen candidate over the existing app and verify:

- [ ] actual candidate bundle ID is `dev.cheatdock.app` before continuing;
- [ ] custom Sheets remain;
- [ ] personal items remain;
- [ ] overlays remain;
- [ ] no duplicate migration occurs;
- [ ] no corruption or migration error appears;
- [ ] stable IDs remain unchanged;
- [ ] filenames remain unchanged where expected;
- [ ] existing Markdown content is preserved;
- [ ] edit/save works;
- [ ] restart persistence works;
- [ ] Open Data Folder resolves to the same identifier-scoped location;
- [ ] Recent/pins remain usable where applicable.

## Uninstall/reinstall retention

Preferably verify:

1. quit Cheat Dock;
2. remove only `/Applications/Cheat Dock.app`;
3. leave Application Support data intact;
4. reinstall the same frozen candidate;
5. use the per-app approval flow again only if macOS requires it;
6. confirm user-authored data reappears.

Deleting the application bundle alone must not intentionally delete user-authored Markdown. Complete data deletion remains an explicit user action after locating the application-owned data with **Open Data Folder**.

## DMG visual qualification

On a physical Mac verify:

- [ ] volume name is sensible;
- [ ] Cheat Dock icon/name displays correctly;
- [ ] Applications destination is obvious;
- [ ] drag-to-install layout is understandable;
- [ ] no clipping or unreadable labels;
- [ ] no broken icon;
- [ ] no unexplained extra files.

Minor aesthetic preferences are not P0 blockers. A broken or confusing install path is a blocker.

## Future optional Developer ID/notarization lane

The existing `signed-notarized-universal` job remains intentionally preserved. It is not executed or required for v0.1 under the current product decision.

If the project later joins the Apple Developer Program and chooses identified Developer ID distribution, that lane can be separately re-qualified with:

- Developer ID Application certificate;
- protected `macos-release` environment;
- current Apple notarization authentication;
- Hardened Runtime and secure timestamp verification;
- notarization acceptance;
- stapling and Gatekeeper verification.

No Apple credential should be created merely to satisfy the current v0.1 gate.

Apple background references:

- https://developer.apple.com/support/developer-id/
- https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution

## Security review

v0.1 distribution qualification must preserve:

- immutable Action pins for release-sensitive workflows;
- checkout credentials disabled after checkout;
- exact source SHA → workflow run → artifact identity;
- ad-hoc signature verified and not misrepresented as Developer ID;
- no `get-task-allow`;
- no new custom entitlement unless separately justified;
- no updater, network/cloud requirement, account, AI, analytics, or telemetry;
- no shell execution capability added to the app;
- no Gatekeeper/SIP disable instructions;
- no quarantine-removal installation instructions;
- no claim that Apple scanned, notarized, trusted, or verified v0.1;
- no accidental tag, Release, or public asset before separate authorization;
- built-in/user Markdown separation and path/symlink protections unchanged.

## v0.1 technical release gate

All of the following must be true before a separate authorized phase creates `v0.1.0`:

- [ ] Normal CI green on the intended source.
- [ ] Distribution-policy PR merged.
- [ ] Final `main` release candidate SHA fixed.
- [ ] Manual universal production workflow green on that exact SHA.
- [ ] Exact candidate is ad-hoc signed and not Developer ID signed.
- [ ] Bundle ID/version/architecture checks pass.
- [ ] DMG mounts and install destination is valid.
- [ ] Exact DMG SHA-256 is recorded.
- [ ] Browser-downloaded/quarantined Gatekeeper test completed.
- [ ] Official macOS per-app approval path works when required.
- [ ] Physical fresh-install/application smoke test passes.
- [ ] Upgrade/user-data-retention test passes.
- [ ] Existing Markdown retention passes.
- [ ] Uninstall/reinstall retention preferably passes.
- [ ] DMG visual review passes.
- [ ] README installation guidance is truthful and includes the non-notarized limitation before install.
- [ ] Content readiness is explicitly classified.
- [ ] No tag, GitHub Release, or public asset is created until separately authorized.

Developer ID signing, Apple notarization, and stapling are **not** v0.1 release gates under the current product decision.

## Release verdicts

Use one of:

- `TECHNICALLY READY FOR GITHUB v0.1 RELEASE` — distribution/physical qualification passes and content is ready.
- `TECHNICALLY READY — CONTENT PR REQUIRED` — technical qualification passes but built-in starter content should be improved before public release.
- `NOT READY` — a technical blocker remains.

This qualification phase stops before creating a tag, GitHub Release, or public DMG.
