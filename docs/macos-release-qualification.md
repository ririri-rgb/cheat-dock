# macOS v0.1 release qualification

This document is the release-engineering gate for the first public Cheat Dock macOS release. It does **not** authorize a tag or GitHub Release by itself.

## Release boundary

The candidate version is `0.1.0`, but this qualification phase must not create:

- a `v0.1.0` tag;
- a GitHub Release;
- permanent/public release assets.

GitHub Actions artifacts generated by the qualification workflow are temporary test artifacts only.

## Release identity

| Property | v0.1 candidate |
| --- | --- |
| Product / Finder name | `Cheat Dock` |
| Rust/npm executable name | `cheat-dock` |
| Bundle identifier | `dev.cheatdock.app` |
| Candidate version | `0.1.0` |
| Version authority | `src-tauri/tauri.conf.json > version` |
| Minimum macOS | `10.15` |
| Distribution architecture | universal `arm64 + x86_64` |
| Bundles | `.app` and DMG |
| Hardened Runtime | enabled |
| Custom entitlements | none |

`package.json`, the root `package-lock.json` package, and `src-tauri/Cargo.toml` mirror the authoritative Tauri version. `npm run release:identity` fails if they drift or if the frozen product/bundle identity changes unexpectedly.

### Why the bundle identifier stays `dev.cheatdock.app`

The identifier is not renamed during this phase. Tauri resolves `app_data_dir` by appending the configured bundle identifier to the OS application-data directory. PR #6 has already placed qualified user Markdown under this identity, so changing it would move the application to a different data directory unless a second migration were introduced.

For macOS this means Cheat Dock user data remains conceptually under:

```text
~/Library/Application Support/dev.cheatdock.app/user-data/
```

Keeping the identifier is a deliberate data-retention decision. Treat it as frozen for v0.1 unless a separately qualified migration is implemented first.

References:

- Tauri PathResolver: https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html
- Tauri distribution/versioning: https://v2.tauri.app/distribute/

## Production build

The release-shaped build is:

```sh
npm ci
npm run release:check
rustup target add aarch64-apple-darwin x86_64-apple-darwin
APPLE_SIGNING_IDENTITY=- npm run tauri build -- --target universal-apple-darwin --bundles app,dmg
```

The ad-hoc build is for structural qualification only. It is **not** suitable for public download.

`.github/workflows/macos-release-qualification.yml` performs this build on the release-qualification PR and verifies:

- generated `.app` exists;
- generated DMG exists and mounts;
- DMG contains the app and Applications link;
- `CFBundleIdentifier` is `dev.cheatdock.app`;
- `CFBundleName` is `Cheat Dock`;
- `CFBundleShortVersionString` matches the candidate version;
- `LSMinimumSystemVersion` matches the configured minimum;
- executable contains both `arm64` and `x86_64` slices;
- code signature is structurally valid;
- no release app enables `com.apple.security.get-task-allow`;
- candidate checksums are recorded.

The workflow uploads the ad-hoc DMG and zipped app as short-lived Actions artifacts for review. They must not be linked as end-user downloads.

Tauri DMG documentation: https://v2.tauri.app/distribute/dmg/

## Signing policy

Public distribution outside the Mac App Store must use a **Developer ID Application** certificate. Do not use an Apple Development, Apple Distribution, ad-hoc, or self-signed identity for the public release.

Tauri configuration keeps `bundle.macOS.hardenedRuntime` explicitly enabled. The current app does not require custom entitlements, so no entitlement exception is added merely for release engineering.

Apple requires Developer ID-distributed software submitted for notarization to use a valid Developer ID signature, Hardened Runtime, secure timestamp, and acceptable entitlements. Tauri's macOS signing path enables Hardened Runtime for signed executables and supports Developer ID/notarization credentials through environment variables.

References:

- Apple notarization requirements: https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution
- Apple Hardened Runtime: https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime
- Tauri macOS signing: https://v2.tauri.app/distribute/sign/macos/

## Notarization policy

Use Apple's current notary service. Do not use deprecated `altool`; Apple requires modern `notarytool`/Notary API workflows.

The manual `signed-notarized-universal` qualification job is gated behind the `macos-release` GitHub Environment and is only started by `workflow_dispatch` with `signed_notarization=true`.

Required secrets:

- `APPLE_CERTIFICATE` — base64 `.p12` containing the Developer ID Application certificate and private key;
- `APPLE_CERTIFICATE_PASSWORD`;
- `APPLE_SIGNING_IDENTITY` — exact Developer ID Application identity;
- `APPLE_API_ISSUER`;
- `APPLE_API_KEY`;
- `APPLE_API_KEY_P8_BASE64` — base64 App Store Connect API private key.

The workflow materializes the API key only in the runner temp directory, runs the normal Tauri production build, then verifies Developer ID signature, Hardened Runtime, Gatekeeper assessment, and the stapled app ticket. Credentials must never be committed.

A successful CI notarization is necessary but is not enough to publish v0.1. The resulting DMG must still pass the physical install/upgrade checklist below.

## Fresh-install qualification

Use the Developer ID-signed and notarized DMG, not the ad-hoc artifact.

Prefer a clean macOS user account or temporarily move aside the existing Cheat Dock application-data directory so the test is actually fresh.

- [ ] Download/copy the candidate DMG through a path that applies normal quarantine metadata.
- [ ] Open the DMG normally in Finder.
- [ ] Gatekeeper does not report the app as damaged or from an unidentified developer.
- [ ] Drag **Cheat Dock** to Applications.
- [ ] Launch `/Applications/Cheat Dock.app` normally.
- [ ] Menu-bar icon appears; normal popup behavior works.
- [ ] No unexpected Accessibility, Files & Folders, camera, microphone, or network permission is requested.
- [ ] Create a small personal Shortcut and Command item.
- [ ] Quit/relaunch and confirm the new Markdown survives.
- [ ] Open Data Folder and confirm the expected identifier-scoped user-data path.

Record macOS version, architecture, DMG SHA-256, app version, and result.

## Upgrade/data-retention qualification

Cheat Dock has no auto-updater in v0.1. Upgrade qualification therefore means replacing the `.app` bundle while preserving Application Support data.

Starting from the currently qualified PR #6/main build with real user data:

- [ ] Back up `~/Library/Application Support/dev.cheatdock.app/` before the test.
- [ ] Confirm existing custom Sheets/overlays are present before upgrade.
- [ ] Install the candidate `Cheat Dock.app` over the previous app in `/Applications`.
- [ ] Launch the candidate and confirm existing data appears without migration prompts or duplication.
- [ ] Confirm custom Sheet stable IDs/files remain unchanged.
- [ ] Add/edit one item with the candidate; restart and confirm persistence.
- [ ] Confirm Recently viewed/pins remain usable where applicable.
- [ ] Confirm Open Data Folder still points to the same identifier-scoped directory.

Deleting only `/Applications/Cheat Dock.app` should not delete Application Support content. Verify reinstalling the same candidate can see retained data.

## DMG and artifact review

Before release:

- [ ] Universal app verified as `arm64 x86_64`.
- [ ] DMG mounts read-only and contains Cheat Dock + Applications destination.
- [ ] Developer ID signature verifies with `codesign --verify --deep --strict`.
- [ ] Gatekeeper `spctl` assessment accepts the installed app.
- [ ] `xcrun stapler validate` accepts the app.
- [ ] Candidate SHA-256 is recorded and matches the file used for physical qualification.
- [ ] DMG visual layout is acceptable on a physical Mac.
- [ ] No debug/dev server URL or development-only permission is present.

## Security review

Release engineering must preserve the existing security model:

- no shell execution capability;
- no updater/network permission added as part of packaging;
- no cloud, account, AI, analytics, or telemetry;
- no custom entitlements unless a concrete feature requires one;
- signing/notarization secrets only in protected CI environment secrets;
- no Developer ID private key in repository files or Actions artifacts;
- no `get-task-allow` in a release signature;
- built-in/user Markdown separation and path/symlink protections unchanged.

## v0.1 release gate

All items below must be true before the separate release phase creates `v0.1.0`:

- [ ] Normal CI is green on the intended release commit.
- [ ] Universal ad-hoc production build qualification is green.
- [ ] Developer ID signed + notarized workflow is green.
- [ ] Fresh-install physical qualification passes.
- [ ] Upgrade/user-data-retention physical qualification passes.
- [ ] DMG/Gatekeeper/stapling checks pass on the exact artifact to publish.
- [ ] README install instructions describe the signed/notarized DMG accurately.
- [ ] Release notes are reviewed.
- [ ] Release commit SHA and artifact SHA-256 are recorded.
- [ ] Only then create the `v0.1.0` tag and GitHub Release in a separate authorized phase.
